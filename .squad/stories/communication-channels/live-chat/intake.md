## Description

```text
Implement the CRM Live Chat channel so customers can start a real-time conversation with the support team and communicate with a human support Agent through the CRM.

Live Chat is a communication channel, not an AI chatbot.

The customer does not choose a specific Agent.

The Live Chat story is responsible for:

- Live Chat conversation/session lifecycle.
- Real-time message exchange between Customer and human Agent.
- Persistence of Live Chat messages.
- Linking the Live Chat conversation to the Customer.
- Linking the Live Chat conversation to an existing Ticket or creating/linking the required Ticket through the existing Ticket Creation functionality.
- Creating the CustomerInteraction generated by the Live Chat communication.
- Integrating the conversation with the CRM's assignment flow.
- Allowing Agents to compose and send outbound Live Chat messages.
- Integrating the existing Quick Replies functionality into the Agent's Live Chat message-composition experience.

The Live Chat story is NOT responsible for deciding which Agent should receive the conversation.

Automatic Agent selection and decision-making belong to Story 23 — Automatic Ticket Assignment.

The Live Chat story must not implement a second independent automatic-assignment algorithm.

The flow must support:

1. Customer opens the Live Chat widget.

2. Customer starts a new Live Chat conversation.

3. The system identifies an existing Customer using the available customer information.

4. If the Customer does not exist, the system creates the required Customer according to the existing Customer Management rules.

5. A Live Chat conversation/session is created and associated with the Customer.

6. The conversation is connected to an existing Ticket when appropriate.

7. If the communication-channel flow requires a new Ticket, the system creates the required Ticket using the existing Ticket Creation functionality from Story 11 without duplicating its core implementation.

8. The Ticket identifies Live Chat as its communication channel/source.

9. A CustomerInteraction is created for the Live Chat communication using the existing CustomerInteraction model/service.

10. The conversation enters the CRM support/assignment flow.

11. The Live Chat flow must pass the conversation/ticket into the supported assignment mechanism rather than choosing an Agent itself.

12. Story 21 must not implement round-robin, first-agent, random-agent, workload-based, availability-based, department-based, branch-based, or any other automatic Agent-selection algorithm.

13. Story 12 provides the existing manual Ticket Assignment capability and Live Chat must remain compatible with it.

14. Story 23 owns Automatic Ticket Assignment rules and decision-making.

15. Story 21 must provide the integration point required for Story 23 to later determine the appropriate Agent without rewriting the Live Chat conversation or messaging implementation.

16. If the assignment mechanism provides an eligible Agent, the conversation can be assigned/handed to that Agent.

17. If no eligible Agent is currently available or no Agent is returned by the assignment mechanism, the conversation remains in a controlled Waiting/Queued state.

18. A waiting conversation must not be assigned randomly or to an arbitrary Agent.

19. When an eligible Agent becomes available, the waiting conversation can continue through the CRM assignment mechanism.

20. The system must support multiple Agents.

21. The customer must not be required to choose or know the Agent.

22. Once an Agent receives the conversation, the Agent can see the Customer information and related Ticket.

23. Customer and Agent can exchange messages in real time.

24. New messages appear without requiring a page refresh.

25. Messages are persisted.

26. The conversation preserves its message history.

27. The conversation remains linked to the Customer and Ticket so the Live Chat communication can participate in the customer's interaction history.

28. The system reuses the existing Customer Interaction History and Ticket History mechanisms rather than creating competing history models.

29. Story 14 remains responsible for TicketHistory only and does not create the Live Chat CustomerInteraction.

30. The system records the appropriate conversation/message events required by the existing history/audit mechanisms.

31. An Agent can access the existing Quick Replies while handling a Live Chat conversation.

32. An Agent can select an available Quick Reply from the Quick Replies list.

33. Selecting a Quick Reply inserts its predefined text into the Live Chat reply input.

34. Selecting a Quick Reply does NOT automatically send the message.

35. The Agent can edit the inserted Quick Reply text before sending.

36. The Agent explicitly sends the final message through the normal Live Chat Send Message action.

37. Quick Reply selection itself does not create a CustomerInteraction or outbound communication record.

38. The actual outbound Live Chat message is persisted and recorded through the normal Live Chat communication flow when the Agent sends it.

39. Quick Replies must reuse the existing Quick Reply functionality and permission model and must not introduce a separate Quick Reply system specifically for Live Chat.

Example business flow:

Customer Marwa opens Live Chat.

Marwa
  ↓
Live Chat
  ↓
Identify/Create Customer
  ↓
Create Live Chat Conversation
  ↓
Link Conversation → Customer
  ↓
Create or Link Ticket
  ↓
Create CustomerInteraction → Live Chat interaction
  ↓
Enter CRM Assignment Flow
  ↓
Assignment mechanism provides Agent?
  ├── YES → Assigned/Delivered to Agent
  │          ↓
  │       Agent opens conversation
  │          ↓
  │       Real-time conversation
  │          ↓
  │       Agent selects Quick Reply (optional)
  │          ↓
  │       Quick Reply text appears in Reply Input
  │          ↓
  │       Agent edits text if needed
  │          ↓
  │       Agent clicks Send
  │          ↓
  │       Message delivered to Marwa
  │          ↓
  │       Message persisted
  │
  └── NO  → Waiting / Queue
             ↓
          Agent becomes eligible/available
             ↓
          CRM Assignment Flow
             ↓
          Agent is determined by the assignment mechanism
             ↓
          Agent receives conversation

Important assignment ownership:

- Story 12 owns manual Ticket Assignment.
- Story 23 owns Automatic Ticket Assignment rules and Agent-selection decision-making.
- Story 21 does not decide which Agent should receive the conversation.
- Story 21 does not implement its own automatic assignment algorithm.
- Story 21 only integrates the Live Chat conversation with the CRM assignment mechanism and handles the resulting assignment/waiting state.
- Story 21 must not duplicate or partially reimplement the rules that will belong to Story 23.

Important CustomerInteraction ownership:

- Story 11 creates CustomerInteraction when a Ticket is created internally through the CRM's Ticket Creation flow.
- Story 19 creates the communication interaction resulting from Email/Web Form.
- Story 20 creates the communication interaction resulting from WhatsApp/SMS.
- Story 21 creates the communication interaction resulting from Live Chat.
- Story 14 is responsible for TicketHistory only and must not create CustomerInteraction.
- Story 21 must reuse the existing CustomerInteraction model/service rather than introducing another interaction-history model.

Quick Replies behavior:

- Quick Replies are reusable response templates available to authorized Agents.
- Quick Replies are a message-composition aid.
- Selecting a Quick Reply only populates the Live Chat reply input.
- Selecting a Quick Reply does not send the message.
- The Agent may modify the inserted text.
- The Agent must explicitly trigger Send Message.
- Only the actual sent message is treated as an outbound Live Chat communication.
- Quick Reply selection alone does not create a CustomerInteraction.
- Live Chat must reuse the existing Quick Reply management and permission functionality.
- Live Chat must not implement Quick Reply CRUD as a separate subsystem.

AI boundary:

- Live Chat in this story is between the Customer and a human Agent.
- No AI-generated responses are implemented.
- No chatbot behavior is implemented.
- AI Chatbot functionality belongs to Story 43.

Real-time communication:

- The project already uses SignalR for real-time functionality.
- Live Chat should reuse the existing SignalR infrastructure where appropriate.
- Messages must be persisted independently from transient real-time delivery.
- Reconnecting or refreshing the page must not silently lose persisted messages.
```

## Acceptance criteria

```text
- [ ] Customer can open the Live Chat interface.
- [ ] Customer can start a new Live Chat conversation.
- [ ] Customer can send a message through Live Chat.
- [ ] Customer can receive Agent messages in real time.
- [ ] Customer does not need to refresh the page to receive new messages.

- [ ] If the Customer does not exist, the system can create the required Customer according to the existing Customer Management rules.
- [ ] Live Chat does not duplicate the Customer creation/profile logic already implemented by Customer Management.

### Conversation and Ticket Linking

- [ ] A Live Chat conversation is created and associated with the Customer.
- [ ] The conversation can be associated with an existing Ticket when appropriate.
- [ ] When the communication-channel flow requires a new Ticket, the system can create/link the Ticket using the existing Ticket Creation functionality from Story 11.
- [ ] Live Chat does not duplicate the core Ticket Creation implementation from Story 11.
- [ ] The resulting Ticket identifies Live Chat as its communication channel/source.

### CustomerInteraction Ownership

- [ ] A Live Chat communication creates the appropriate CustomerInteraction record.
- [ ] The CustomerInteraction is associated with the correct Customer.
- [ ] When applicable, the CustomerInteraction is associated with the relevant Ticket and Live Chat conversation.
- [ ] Live Chat interaction data is available through the existing Customer Interaction History mechanisms from Story 08.
- [ ] Story 21 reuses the existing CustomerInteraction model/service.
- [ ] Story 21 does not introduce a competing CustomerInteraction/history model.
- [ ] Story 14 remains responsible for TicketHistory only.
- [ ] Story 14 does not create the Live Chat CustomerInteraction.

### Assignment Integration

- [ ] Live Chat supports multiple Agents.
- [ ] The customer does not choose the Agent.
- [ ] Live Chat does not select an Agent directly.
- [ ] Live Chat does not simply select the first Agent in the database.
- [ ] Live Chat does not assign the conversation to an arbitrary Agent.
- [ ] Live Chat does not implement a round-robin assignment algorithm.
- [ ] Live Chat does not implement a random assignment algorithm.
- [ ] Live Chat does not implement workload-based automatic assignment.
- [ ] Live Chat does not implement availability-based automatic assignment.
- [ ] Live Chat does not implement department-based or branch-based automatic assignment.
- [ ] Live Chat does not implement any other independent automatic Agent-selection algorithm.
- [ ] Live Chat enters/uses the CRM assignment mechanism.
- [ ] The existing manual Ticket Assignment functionality from Story 12 remains compatible with Live Chat.
- [ ] Story 21 provides a clear integration point for Story 23.
- [ ] Story 23 can later determine the appropriate Agent according to the CRM's automatic assignment rules without requiring the Live Chat conversation/message implementation to be rewritten.

### Agent Availability and Queue

- [ ] The Live Chat flow does not assume that an Agent is always available.
- [ ] If the CRM assignment mechanism provides an eligible Agent, the conversation can be assigned/delivered to that Agent.
- [ ] If no eligible Agent is currently available or no Agent is returned by the assignment mechanism, the conversation remains in a controlled Waiting/Queued state.
- [ ] A waiting conversation is not lost.
- [ ] A waiting conversation is not assigned randomly.
- [ ] A waiting conversation is not assigned to an arbitrary Agent.
- [ ] When an eligible Agent becomes available, the conversation can continue through the CRM assignment mechanism.

Example:

Marwa starts a Live Chat.

There are three Agents:

- Agent A
- Agent B
- Agent C

Live Chat does not choose A, B, or C itself.

The conversation enters the CRM assignment mechanism.

If the assignment mechanism determines Agent B:

Marwa → Live Chat → Ticket → Assignment Mechanism → Agent B

Agent B receives the conversation and communicates with Marwa in real time.

If the assignment mechanism cannot currently provide an eligible Agent:

Marwa → Live Chat → Ticket → Waiting Queue

When an eligible Agent becomes available, the conversation can continue through the CRM assignment mechanism.

### Real-time Messaging

- [ ] Agent can send messages to the Customer.
- [ ] Customer can send messages to the Agent.
- [ ] Messages are delivered in real time.
- [ ] Messages are persisted.
- [ ] Conversation history remains available after reconnecting.
- [ ] Conversation history remains available when reopening the conversation.
- [ ] Message ordering is preserved.
- [ ] Disconnect/reconnect scenarios do not silently lose persisted messages.

### Quick Replies

- [ ] An authorized Agent handling a Live Chat conversation can access available Quick Replies.
- [ ] The Agent can open/select a Quick Reply from the existing Quick Replies list.
- [ ] Selecting a Quick Reply inserts its predefined text into the Live Chat reply input.
- [ ] Selecting a Quick Reply does not automatically send the message.
- [ ] The Agent can edit the inserted Quick Reply text before sending.
- [ ] The Agent must explicitly click/use Send Message to send the response.
- [ ] The selected Quick Reply itself does not create a CustomerInteraction.
- [ ] The selected Quick Reply itself does not create an outbound communication record.
- [ ] After the Agent sends the message, the actual outbound Live Chat message is persisted.
- [ ] The sent message is associated with the correct Customer, Ticket and Live Chat conversation.
- [ ] Quick Reply access respects the existing Agent permissions.
- [ ] Agents cannot use Quick Replies they are not authorized to access.
- [ ] Live Chat does not introduce a separate Quick Reply CRUD/management system.

### Conversation Lifecycle

- [ ] A Live Chat conversation has a clear lifecycle/state such as Waiting, Active, and Closed according to the final domain model.
- [ ] A Waiting conversation can become Active when an Agent receives it.
- [ ] A Closed conversation cannot continue normal Agent responses unless explicitly reopened according to the defined business rules.
- [ ] Closing a conversation does not delete its message history.

### CRM History

- [ ] The Live Chat communication is represented in the Customer's interaction/history data through the existing CustomerInteraction mechanism.
- [ ] Live Chat reuses the existing Customer Interaction History implementation from Story 08.
- [ ] TicketHistory mechanisms from Story 14 are reused where applicable.
- [ ] Live Chat does not create a second competing history model for Ticket changes.
- [ ] Story 14 remains responsible for TicketHistory only.
- [ ] Story 14 does not create the Live Chat CustomerInteraction.

### Human Agent vs AI

- [ ] Live Chat is between Customer and human Agent.
- [ ] No AI-generated response is required.
- [ ] No chatbot behavior is implemented.
- [ ] AI Chatbot functionality remains out of scope and belongs to Story 43.

### SignalR / Real-Time

- [ ] The existing SignalR infrastructure is reused where appropriate.
- [ ] Customer and Agent receive new messages without manually refreshing the page.
- [ ] Persisted messages remain available after a SignalR reconnect.
- [ ] The implementation does not require a message broker unless the existing architecture requires one.
```
